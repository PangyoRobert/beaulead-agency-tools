# Ecommerce Unit Economics

자사몰 1종을 기준으로 상품값·택배비·카드 수수료를 넣으면 묶음 판매(단품·1+1·2+1·3+1·4+1)별로
광고비를 쓰기 전에 남는 돈, 본전이 되는 광고 효율, 주문 1건에 쓸 수 있는 최대 광고비를 바로
계산하는 대면 시연용 시뮬레이터입니다. 전문용어는 쉬운 말로 풀어 쓰고 작은 글씨로 병기합니다.

## 파일

| 파일 | 역할 |
| --- | --- |
| `economics-config.js` | 가상 예시 기본값, 판정 기준값, 묶음 구성, VAT율, **용어 사전(`glossary`)**. 값과 문구가 바뀌는 곳은 여기뿐입니다. |
| `calculator.js` | 계산 공식과 입력 검증. Node와 브라우저에서 같이 씁니다. |
| `explain.js` | 계산 결과를 쉬운 말 문장과 단계별 계산 과정으로 풀어 씁니다. 숫자를 새로 계산하지 않습니다. |
| `index.html` | 입력과 결과를 그립니다. 숫자와 전문용어를 따로 적어 두지 않습니다. |

## 쉬운 말 원칙

읽는 사람은 마케팅 용어를 모르는 사업주와 입문 마케터이고, 고등학생도 이해할 수 있는 수준을 기준으로 하되
**짧게** 씁니다. 처음에는 항목마다 한 줄·자세히·예시·주의의 4단으로 22개를 풀었는데, 현장에서 쓰기엔 너무 길어
2026-10-08에 줄였습니다(풀이 본문 3,736자 → 약 1,150자).

- **쉬운 말을 크게, 전문용어는 작게 병기합니다.** 다른 곳에서 그 말을 들어도 이어서 이해하게 하려는 것입니다.
  예) "광고비 쓰기 전에 남는 돈" + 작은 글씨 "광고 전 공헌이익 (CM1)"
- **모든 항목(22개)** 은 쉬운 말 + 병기 + 한 줄 풀이를 가집니다. 입력 칸 아래 힌트와 표의 줄 이름에 쓰입니다.
- **ⓘ와 아래 「용어 풀이」 목록은 핵심 11개에만** 있습니다(`glossaryOrder`). 목록에서는 한 줄 풀이가 기본이고,
  핵심 6개(남는 돈, 100원 팔면 남는 돈, 본전 광고 효율, 최대 광고비, 주문 1건당 광고비, 묶음 구성)에만 예시 한 줄,
  오해하면 틀리는 4가지에만 주의를 둡니다: 순이익이 아니다 / 부가세를 안 빼서 약 10% 크게 나온다 / 첫 구매 기준이다 /
  플랫폼마다 광고비 기준이 달라 광고 관리자 숫자는 먼저 확인한다. 긴 설명(`detail`)은 두지 않습니다.
- 광고비까지 쓰고 남는 돈은 **진짜 이익이지만 순이익은 아닙니다**(인건비·임대료 같은 고정비를 아직 빼지 않았고, 반품·취소도
  반영하지 않았습니다).
- 「한눈에 보기」는 입력이 바뀌면 같이 바뀌는 문장 요약이고, 「이렇게 계산했어요」는 지금 입력한 숫자로 계산 과정을 한 줄씩
  보여줍니다. 둘 다 `calculator.js`가 계산한 값을 글로 옮길 뿐입니다.
- 본전 광고 효율은 배(1.33)가 아니라 **%(132.9%)** 로 씁니다. 광고 관리자에서 흔히 보는 표기이고, "광고비 100원당 결제금액
  132.9원"이라는 문장을 함께 붙입니다.
- "법칙"이라는 말은 쓰지 않습니다. 뷰리드 기획 기준이지 법칙이 아니라서 "점검 ①·②"로 부르고, 전문 표기(제1·제3법칙)는 병기합니다.

문구를 바꿀 때는 `glossary`만 고칩니다. 테스트가 아래를 지켜 줍니다.

- 쉬운 말(`plain`), 한 줄 풀이, 예시, 주의에 전문용어(CM1·ROAS·CPA·PG·VAT 등)가 새어 나오지 않는다.
- **풀이가 길어지지 않는다**: 항목마다 글자 수 상한이 있고 `detail`은 둘 수 없으며, 풀이 본문 합계도 1,300자를 넘지 못한다.
- **예시의 숫자는 `glossaryExample`로 실제 계산한 값과 같다.** 글과 계산이 어긋나면 실패한다.
- 광고 관리자 숫자를 "같은 기준"이라거나 "보이는 그대로 넣으라"고 단정하는 문구가 없다.
- 화면에 직접 적힌 글에도 전문용어가 단독으로 나오지 않는다(괄호 병기만 허용). 생성되는 문장에도 전문용어가 없다.

## 기본값은 전부 가상 예시다

`defaults`는 실제 상품이나 고객사의 값이 아닙니다. 대면 미팅에서 바로 보여주려고 미리 채운
예시이며 화면에도 "가상 예시"라고 표시합니다. 공개 저장소이므로 실제 원가·마진은 넣지 않습니다.

## 어떤 방식을 채택했나

**입력이 같으면 결과가 항상 같은 회계 항등식만 씁니다.** 실제 손익과 어긋날 여지가 입력값의
정확도뿐이도록 했습니다.

- 채택: 광고 전 공헌이익(CM1), CM1율, 손익분기 ROAS, 한계 CPA, 개당 배송비, 제1·제3법칙 판정
- 뺀 것: 재구매·LTV 기반 CAC, 번들마다 같은 CPA를 가정하는 최종 마진, 소진 주기 기반 대량번들
  제한, 판정식을 확인하지 못한 제2법칙과 "추천/반려" 조합 판정
- **반품·취소는 반영하지 않는다(0% 가정).** 화면 결과 옆에 항상 이 전제를 적습니다.

## 금액 기준: 모든 금액을 부가세 포함으로 본다 (2026-10-08 사용자 결정)

- 판매가·상품값·택배·포장비는 **가격표·영수증에 보이는 그대로(부가세 포함)** 넣고, 광고비(CPA)는 부가세 포함 금액으로 맞춰 넣습니다.
  부가세를 따로 빼는 환산은 하지 않고, 그래서 `vatRate` 설정도 공급가 필드도 없습니다.
- 계산은 사용자 시트와 같습니다(`남는 돈 = 결제금액 − 상품값 − 카드 수수료 − 택배·포장비`). 시트를 그대로 재현하는 값을
  테스트로 고정했고, 그래서 판정 기준값(결제금액 4만 원 / 남는 돈 2.5만 원 / 60%)도 시트와 같은 뜻입니다.
- 손익분기 ROAS = 결제금액 ÷ 남는 돈.
- **부작용(사용자가 감안하기로 함):** 부가세를 따로 빼지 않기 때문에, 모든 금액에 부가세가 들어 있다면 남는 돈은
  부가세를 뺐을 때보다 대체로 약 10% 크게 나옵니다(납부할 부가세만큼). 화면과 용어 풀이에 이 주의를 적었습니다.
  일부 금액이 부가세 없이 입력되면 오차가 더 커질 수 있습니다.
- 광고 관리자의 광고비·ROAS는 플랫폼마다 부가세 포함 여부와 매출을 세는 방식이 달라서, 판매가·상품값·택배비는 가격표·영수증
  그대로, **광고비는 광고 관리자 숫자의 부가세 포함 여부를 먼저 확인해 맞춰 넣으라**고 안내합니다.

## 판정 기준값은 뷰리드 기획 기준이다

결제금액 4만 원 / CM1 2.5만 원(둘 중 하나 이상), CM1율 60%는 사용자의 시트 「이커머스 사전 계산
시스템」 5대 불문율에서 가져온 값입니다. 시장 표준이나 실측치가 아니라서 화면에서 바꿀 수 있게
열어 두었습니다. 값을 영구히 바꾸려면 `economics-config.js`의 `thresholds`만 고칩니다.

## 입력은 밖으로 나가지 않는다

계산은 브라우저 안에서만 합니다. `localStorage`, URL 파라미터, 네트워크 전송을 쓰지 않고
`scripts/test_ecommerce_unit_economics.js`가 그 경로가 없는지 검사합니다. ⓘ 풀이도 주소를 바꾸지 않고
그 자리에서 엽니다.
